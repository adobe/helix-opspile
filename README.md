# helix-opspile

An inbox for opsophiles: one place for an ops team to work through every Slack, Microsoft
Teams and Discord channel it is responsible for, with per-person and per-team read state.

Status: **all four piles live.** Signed Slack events are stored in R2 and queued for
normalization; Teams: a cron keeps one tenant-wide Graph subscription alive, and its
notifications and the messages they name are stored the same way; Discord: a Durable Object
polls the servers it reads every minute and stores their new messages, and every few minutes
the last day's edits, deletions and reactions (pile 1). A queue consumer
turns every raw object into one markdown file per message (pile 2), filed by the channel rules
in D1, and labels, re-threads and titles the threads with Workers AI. The inbox (pile 4) shows
them per team with read state, status piles, filters, replies, reactions, ✅ to resolve and
shared drafts, all as the person signed in; the admin pages manage teams, members, rules and
customers, and the knowledge-base editor the knowledge bases (pile 3). Thread agents draft
replies and fill the knowledge bases in the channels where they are switched on. Agents outside
the browser work the inbox through `/mcp`, and agents in the browser through WebMCP. See
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the design and the open issues for what
comes next.

## Ingest Worker

One Cloudflare Worker, deployed as `helix-opspile-prod` and `helix-opspile-stage`. Production
answers on its custom domain (`WORKER_DOMAINS`, the `PUBLIC_ORIGIN`); its `workers.dev` address
stays on as a retired origin (`RETIRED_ORIGINS`): pages there redirect, and machine endpoints
still answer.

| `GET /api/me`, `/api/inbox?team=`, `/api/inbox?view=personal`, `/api/thread?thread=` | The signed-in person, a team's threads with read state, unread mentions of the viewer (`unreadMentions`) and who each waits on (`waiting_on`: Clef's next actor, but never `us` when Adobe posted last), the personal view's threads (the conversations in the channels the viewer posted or was mentioned in, whichever team they are filed under, with the view's `rooms`), one thread's messages from pile 2. A thread also carries `mentioned`: who the people its messages `@`-mention are (Adobe, partner, customer or bot), by name, so the page sets mentions of people outside Adobe apart, and `can_post_as_bot`: whether the viewer may send as the opspile app there (`POST /api/post/app`). `GET /api/me` also says which rooms the inbox listens to (`rooms`: the person's teams, and the teams the channels of their personal view are filed under). | `GET /api/search?team=&q=`, `/api/search?view=personal&q=` | Search over a team's inbox (or the personal view), on every platform at once (`src/search.js`): threads about `q` by meaning (the `CONTENT` vectors of their messages and of the threads as a whole), threads with a message that has every word of `q` (BM25 over the `SEARCH` items) and threads whose title, channel, customer or facts have its words, best match first. The entries come as `/api/inbox` shapes them, with `hits` in order: why each matched (`title`, `place`, `fact`, `text`, `topic`) and the message that matched best (`snippet`). |
| `GET /api/review/queue`, `GET /api/review/stats`, `POST /api/review` | Label review for members of the `admin` team: unreviewed labels (least confident first), Clef's agreement per question, and a correction for one question of one label. |
| `POST /api/post` | Reply in a thread **as the signed-in person**, through their own Slack or Microsoft account. `409` with `connect` when they have not connected it yet. Only staff, only in their teams. `mentions` (account ids) turn each `@Name` of those accounts into a real Slack (`<@U…>`) or Teams (`<at>`) mention, so the person is notified. Emoji `:names:` go out as the platform knows them (another platform's name becomes Slack's, a name nobody has the emoji Clef picks, see docs/ARCHITECTURE.md "Replying"); `text` in the answer is the reply as sent. With files, the body is `multipart/form-data`: the JSON as `payload`, each file as `files` (up to 10; `src/attach.js`). | `POST /api/edit` | Edit a message one sent, `{ thread, id, text, mentions? }` (`thread` is the message's platform thread, as for `/api/react`), the way it was sent (`src/edit.js`): one's own message **as the signed-in person** (Slack `chat.update` with their token; Teams `PATCH` on the channel message or reply, which needs `ChannelMessage.ReadWrite`, see `TEAMS_EDITS`; not on Discord, which lets only bots edit), or a message one posted **as the opspile app** (recorded in `app_posts`) as the app (Slack `chat.update` with the bot token, the Teams bot's update activity, Discord `PATCH`), where the app may still post. Only staff, only in their teams. |
| `POST /api/react` | Add (or with `remove`, take off) a reaction on one message **as the signed-in person**: `{ thread, id, emoji }`, where `thread` is the message's platform thread and `emoji` a picker name (`thumbsup`, `white_check_mark`, …) or a reaction as the thread shows it. | `POST /api/resolve` | `{ thread, undo? }`: ✅ on the root message of the entry's latest platform thread, as the signed-in person (`white_check_mark` on Slack, `✅` on Teams), or with `undo` take their ✅ off every root of the entry. | `GET`, `PUT`, `DELETE /api/draft` | The thread's shared draft (at most one per inbox entry), seen by everyone in the teams that follow the channel (the team it is filed under, and those it is shared with). `PUT { thread, text, mentions?, base }` saves it as the signed-in person, `DELETE { thread, base? }` discards it (a draft the thread's agent saved: the agent hears who discarded it); `base` is the `updated_at` of the draft the text was written from, and a draft that changed since answers `409` with the current one. `POST /api/post` or `/api/post/app` with `draft: <base>` uses the draft up. | cron `*/20 * * * *` | Creates missing team knowledge bases (pile 3), and imports or refreshes the Artifacts mirrors of the GitHub repositories agents may read. ### Inbox and Access

`/inbox` and `/api` (with `/inbox/admin` and `/inbox/kb` under them) are one Cloudflare
Access application. People sign in with **Slack** (Slack's OpenID Connect, through the opspile
Slack app), **Microsoft** (Entra ID, the opspile app registration, our tenant only) or a
**one-time code** by email. Whichever they use, the application's allow policy decides, by
email: it lists the staff members of the ops teams, and the Worker keeps it so (see
`ACCESS_APP_ID` above) after every membership change in the admin pages and on the cron. The
Worker trusts only a verified `Cf-Access-Jwt-Assertion` whose email is a person in D1 on an ops
team, and shows them the threads of their own teams.

**No-team mode.** With `SIGNIN_DOMAINS`, anyone with an email at one of those domains may sign
in too, team or not (the policy gets those domains, see `SIGNIN_DOMAINS` above). Someone on no
team becomes a person in D1 when they first sign in, if they are not one yet (staff if the
domain is a staff domain), and has only the personal view. The MCP server's `list_threads` and
`search_threads` are of that view for them. Without `SIGNIN_DOMAINS`, only team members get in.

**The personal view** is everyone's, on a team or not: the conversations in the channels one
posted or was mentioned in, whichever team they are filed under. Anyone reads, replies, reacts,
resolves, drafts and seeds agents in those threads, as well as in their teams' inboxes. The inbox
listens to the rooms of the teams those channels are filed under (`/api/me`'s `rooms`); in a
room of a team one is not on, the socket is *scoped* (`src/room.js`): it hears only about the
threads of the channels of one's personal view (`recipients` in `src/shares.js`).

Access returns to the requested path after a Slack or Microsoft login, but without its query
string; pages that need parameters across a sign-in carry them in the path (see the OAuth
consent page below). Both identity providers redirect to
`https://<team>.cloudflareaccess.com/cdn-cgi/access/callback`, which must be listed in the
Slack app's redirect URLs and the Entra app's web redirect URIs.

### MCP server

`/mcp` lets an agent outside the browser (Claude, an IDE, a CLI) work the inbox as the person
signed in, with sixteen tools: `whoami`, `list_threads`, `search_threads` (what `/api/search`
finds, in all of the person's teams), `get_thread`, `post_draft`, `post_as_user`,
`post_as_bot`, `react_to_message`, `resolve_thread`, `seed_agent`, and the extraction rules and
tech stack of a team (`list_extraction_rules`, `test_extraction_rule`, `save_extraction_rule`,
`delete_extraction_rule`, `save_tech`, `delete_tech`; the changes for the admin team and the
team's managers), so an agent can be asked to update the rules. A thread
is answered three ways, as in the inbox: `post_draft` saves its shared draft (`PUT /api/draft`;
`base` names the version it replaces), which the team sees and sends, with the `sources` it
rests on, which only the team sees; `post_as_user` posts as
the person (`POST /api/post`); `post_as_bot` posts as the opspile app (`POST /api/post/app`),
where the channel lets the app post. Both post tools take the shared draft's version as
`draft`, which uses it up; `get_thread` shows the draft and `can_post_as_bot`.

The admin team gets more tools, which nobody else sees in `tools/list` (for them it is
`cacheScope: private`) or can call (an unknown tool):

| Tool | What |
| --- | --- |
| `get_thread_trace` | Any thread like `get_thread`, with its agent's work in the same timeline, oldest first: what it was told, what it thought and said, every tool call with its arguments and result, and every MCP server call a code mode script made (`mcp_call`: arguments and status, not results; the agent keeps its latest 200); its prompt and tool changes; its model, tools, MCP servers, latest turn and token use. From the agent's transcript since its last reset; `limit`, `before` (paging) and `max_chars`. A channel without agents has no trace (its agent is not started to look). |

It speaks MCP `2026-07-28`
over Streamable HTTP: stateless, `server/discover`, version and capabilities in each
request's `_meta`, header checks (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`), caching
hints, and plain JSON responses (no SSE, no `subscriptions/listen`). Clients of the 2025
revisions get `initialize` and the same tools, without a session. `post_as_user` and `post_as_bot` ask the user to
confirm before posting (a multi round-trip `elicitation/create`) when the client supports
elicitation; otherwise the client's own tool approval is the check. `get_thread` does not mark
anything read.

Sign-in is OAuth 2.1, served by the Worker itself (`src/oauth.js`): discovery
(`/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`), open
dynamic client registration (`/oauth/register`, any https redirect URI or localhost), and
`/oauth/token` (PKCE S256, refresh tokens rotated). There is no list of allowed clients:
`/oauth/authorize` (public) signs the request into the path of the consent page `/api/oauth/consent/…`, behind Access like the rest of `/api` (Access keeps the path through a Slack or Microsoft login but drops the query); it shows who
asks and, in large type, the host the grant goes to, and the person decides. Codes and
tokens are stored hashed in D1 (`oauth_*`, migration 0015); an access token lives an hour.
`/mcp` itself is **not** behind Access; it takes these tokens (or an Access assertion, for
`cloudflared access curl`). Connect a client to `<origin>/mcp`.

### Thread agents

An agent per thread in the channels where agents are on follows the thread, keeps its
shared draft current (a person sends it), and fills the customer's and the team's knowledge
bases (OKF; see ARCHITECTURE, "Thread agents"). To turn them on:

1. Create an AI Gateway in the Worker's account (`AGENT_GATEWAY` is its id). Leave it
   unauthenticated, or create a token and set the secret `AI_GATEWAY_TOKEN`.
2. Create an [Amazon Bedrock API key](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html)
   that may invoke the model's inference profile in `AGENT_REGION`, and set it as the Worker
   secret `BEDROCK_API_KEY` (`npx wrangler secret put BEDROCK_API_KEY --name helix-opspile-prod`).
3. Export `AGENT_MODEL`, `AGENT_GATEWAY` and, optionally, `AGENT_CHANNELS` (and for CI, add
   them as repository secrets), apply the migrations and deploy.
4. Turn agents on or off per channel in the knowledge-base editor (`/inbox/kb`, **Thread
   agents**): the admin team for every channel, team managers for their teams' channels.

GitHub repositories the agents may read are rows in `agent_repos`, data like the rules:
`INSERT INTO agent_repos (scope, slug, url, note) VALUES ('org', 'acme', 'https://github.com/acme/site', 'their site')`
(`scope` is `all`, `team` or `org`). The cron mirrors them into Artifacts within 20 minutes.
`GET /diag/agent?name=<thread key>` shows what an agent is doing (and its MCP servers); the
admin team sees everything it did with the MCP tool `get_thread_trace`.

**MCP servers.** Each ops team and each customer can have MCP servers for its agents, added in
the knowledge-base editor (`/inbox/kb`, **MCP servers** of the team's or the customer's
knowledge base; whoever may edit it): a name, the server's `https://` Streamable HTTP URL, what
it is for, its credentials, and optionally the only tools agents may call. Credentials are
either request headers (sealed with `TOKEN_KEY`, never shown again) or an **OAuth** sign-in:
**Connect** sends whoever manages the server to the server's own sign-in (opspile finds its
authorization server, registers itself there unless a client id is given, and uses PKCE), and
the agents then call the server **as that person**, with what they may do there, until someone
disconnects it. Tokens are refreshed as they expire, one refresh at a time for all agents, and
the cron refreshes grants unused for a week so that refresh tokens stay alive. For a server that
does not let clients register themselves, register one with the redirect URI
`<PUBLIC_ORIGIN>/api/kb/mcp/oauth/callback` and give its client id (and secret). Adding a server
connects to it and lists its tools. An agent gets the servers of its thread's team and customer,
and calls them only from code mode scripts (`await tools.mcp__<name>__<tool>(args)`); see
ARCHITECTURE, "Thread agents".

opspile's own `/mcp` is such a server: added with the URL `<PUBLIC_ORIGIN>/mcp` and **OAuth**,
and connected by someone, it gives the agents what that person sees in the inbox (and their
posting tools: limit it with **Only these tools**, e.g. `list_threads, search_threads,
get_thread, get_thread_trace`).

**Global MCP servers.** Two servers are built in, set up once for every team, and off until
the admin team or a team's managers turn them on, for the team (in the team's knowledge base,
**MCP servers**) or for one channel (**Per channel**; a channel's switch wins over its team's):

- **`browser`**, Cloudflare's hosted [Browser Run MCP server](https://github.com/cloudflare/mcp-server-cloudflare/tree/main/apps/browser-rendering):
  pages as markdown or HTML, screenshots, PDFs, links, elements by selector, JSON extraction,
  crawls. It needs the secret `BROWSER_RUN_TOKEN`: an account API token with *Browser Run
  Write* only.
- **`github`**, [GitHub's MCP server](https://github.com/github/github-mcp-server), read-only
  (`/mcp/readonly`, lockdown mode), as the opspile **GitHub App**: it reads exactly the
  repositories the app is installed on. To set it up, a member of the admin team opens
  **MCP servers** of any team's knowledge base, fills in the GitHub organization that should
  own the app (or nothing, for their own account) and **Create on GitHub**; GitHub asks to
  confirm, opspile keeps the app and sends them on to install it, on all of an account's
  repositories or a selection. The app is public, so it can be installed on any account
  (customers' organizations too), and so anyone can install it: an installation counts only
  once the admin team **Allow**s it in the same place (and **Revoke** takes it back).
  **Install elsewhere or change repositories** changes where it is installed. With several
  allowed installations, the server is there once per account (`github_<account>`). The app
  only asks for read access; it needs no webhook.

See ARCHITECTURE, "Global MCP servers".

**Agent tools.** Two of the agents' tools are off until the admin team or a team's managers
turn them on, the same way and on the same page (**Tools and MCP servers**, group **Tools**):
for the team, or for one channel (**Per channel**; a channel's switch wins over its team's):

- **`post_message`**: the agent posts a reply in its thread right away, as the opspile bot of
  the platform, next to keeping the draft. The Slack app needs the bot scope `chat:write`
  (reinstall it after adding the scope), the Discord bot the *Send Messages* and *Send
  Messages in Threads* permissions; Teams needs the opspile Teams bot (below). A platform
  whose bot is not set up does not get the tool.
- **`computer`**: pi's `bash` tool, on [Cloudflare Computer](https://github.com/cloudflare/computer):
  a just-bash shell in a Dynamic Worker (the `LOADER` binding) over a working directory per
  thread that keeps its files, with `jq` and `curl`. The shell reaches the internet without a
  filter, so what an agent read can leave through it; the prompt says not to send anything to
  sites that are not the customer's or Adobe's.

**The opspile Teams bot.** Microsoft Graph lets no app post to a channel; a Bot Framework bot
can, in the teams it is installed in. The bot is the opspile Entra app itself:

1. Register it with the Bot Framework: an Azure Bot (F0, kind `azurebot`) in any subscription,
   *Single tenant*, with the existing app (`MS_CLIENT_ID`, tenant `MS_TENANT_ID`), messaging
   endpoint `<PUBLIC_ORIGIN>/teams/bot`, and the Microsoft Teams channel on.
2. Add the Graph application permission `TeamsAppInstallation.ReadWriteSelfForTeam.All` to the
   app, and have an admin grant consent: with it the app installs itself (and only itself) in a
   team on its first post there.
3. Build the Teams app package with `node scripts/teams-app.mjs` (from `MS_CLIENT_ID` and
   `PUBLIC_ORIGIN`; written outside the repo) and have a Teams admin upload it to the org
   catalog (Teams admin center, **Manage apps**, **Upload new app**).
4. Set `TEAMS_APP_ID` to the app's id in the catalog (Graph `appCatalogs/teamsApps`, not the
   manifest id) and deploy.

See ARCHITECTURE, "Agent tools".

### Rules and replay

Rows in the `rules` table map a channel to an ops team, an org and a kind: for each target,
the matching rule with the lowest `priority` wins. `field` is `channel_id`, `name`,
`group_name` (the Teams team) or `connected` (Slack Connect team ids); `pattern` is a
case-insensitive regular expression and `value` may use `$1`. For example
`org | name | ^aem-(.+)$ | $1` files `aem-acme` under the org `acme`.

The admin team edits teams, members, rules, manual assignments and orgs at `/inbox/admin`,
which also re-files the channels a change moves. Rules changed in D1 by hand need a replay
with `--clear`.

Rows in `partner_domains` (`domain`, `name`) mark people from a partner's mail domain (or a
subdomain of it) as partners on their profile card, instead of customers:
`INSERT INTO partner_domains (domain, name) VALUES ('agency.example', 'Agency')`.

Pile 2 is derived, so it can always be rebuilt from pile 1:

```sh
node scripts/replay.mjs --dry-run           # count what would be replayed
node scripts/replay.mjs --prefix slack/     # replay part of pile 1
node scripts/replay.mjs                     # after raising FORMAT (src/channels.js): rewrite what renders differently
node scripts/replay.mjs --clear             # after changing rules: empty pile 2, replay all
node scripts/replay.mjs --rethread          # redo re-threading for every root (after a replay)
node scripts/replay.mjs --rethread --channel <id>   # redo one channel's, oldest root first
node scripts/replay.mjs --relabel           # label every thread again (titles, Clef, tech stack)
node scripts/replay.mjs --vectorize         # embed every channel thread and its messages again
```

The Entra app needs these Microsoft Graph **application** permissions, with admin consent:
`Team.ReadBasic.All`, `Channel.ReadBasic.All`, `ChannelMessage.Read.All`, `User.Read.All`, and
`TeamsAppInstallation.ReadForTeam.All` (the cron lists each Teams team's installed bots, so replies
can mention them; `/diag/teams?bots=1` runs that once). `TeamMember.Read.All` is optional: with it,
the channel suggestions on the admin pages count the members of a Teams team who never post; without
it they go by posts and reactions there. On Slack they use `conversations.members`, which needs the
bot scopes `channels:read` (and `groups:read` for private channels).
`Files.Read.All` (or `Sites.Read.All`) is optional too: with it, the files attached to Teams
messages (SharePoint and OneDrive) are copied into pile 1 and their images shown in the inbox;
without it they stay links. Images pasted into a message (hosted contents) need only
`ChannelMessage.Read.All`.
For replies and reactions it also needs the **delegated** permissions `ChannelMessage.Send`
(which covers `setReaction`/`unsetReaction` on channel messages and inline images in replies),
`offline_access` and `User.Read`, for files other than images in replies `Files.ReadWrite.All`
(asked for only when someone attaches one), and the web redirect URI
`<origin>/api/auth/teams/callback`; editing one's own
Teams messages from the inbox also needs the delegated `ChannelMessage.ReadWrite` (admin consent,
then `TEAMS_EDITS`); for signing in to
the inbox, the web redirect URI of Access's callback and a client secret held by Access. The
Slack app needs the user scopes `chat:write`, `reactions:write` and `files:write` (the last
asked for only when someone first attaches a file to a reply) and the redirect URLs
`<origin>/api/auth/slack/callback` and Access's callback (Sign in with Slack asks for
`openid`, `email` and `profile` itself); the bot needs `team:read` for the workspace that links to
Slack open in (`team.info`), `reactions:read` for the reaction
events, `emoji:read` for the workspace's custom emoji (`emoji.list`, so a custom `:name:` in a
reply stays as typed; without it Clef replaces no name on Slack that is not a standard one,
since it may be a custom emoji), `files:read` for images and for the files shared in Slack Connect channels (their
events carry only a stub, which opspile looks up with `files.info`), and `files:write` for files
sent as the opspile app. Its Event Subscriptions request URL is
`<origin>/slack/events`.

### Discord

A Discord application reads the servers in `DISCORD_GUILDS` through its bot, read-only:

1. Create the application in the [Developer Portal](https://discord.com/developers/applications);
   under **Bot**, turn on the **Message Content** intent (privileged; no review below 100 servers)
   and turn off **Public Bot** (first set **Installation › Install Link** to *None*). Set the
   bot's token as `DISCORD_BOT_TOKEN` (`cf workers secrets update DISCORD_BOT_TOKEN --worker
   helix-opspile-prod --type secret_text --text …`).
2. Add the bot to each server with the permissions *View Channels* and *Read Message History*
   (`https://discord.com/oauth2/authorize?client_id=<app id>&scope=bot&permissions=66560&guild_id=<guild id>`).
   It sees the channels those permissions open to it; private channels need a role.
3. Export `DISCORD_GUILDS` (and for CI, add it as a repository secret), and deploy. The cron
   starts the poller; `POST /diag/discord` polls at once. The first poll reads
   `DISCORD_HISTORY_DAYS` of history.
4. Optionally, `DISCORD_STAFF_ROLES` names the server roles of Adobe people, and with
   `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` (OAuth2 redirect
   `<origin>/api/auth/discord/callback`) people connect their Discord account in the inbox.

Discord lets only bots post and react through its API, and opspile acts as the person or not at
all: Discord threads have no reply box, reactions or ✅ in the inbox, only a link to reply in
Discord. Rules match the channel's `name`, and `group_name` is the server's name.

Discord has no webhooks for messages, only a gateway WebSocket, which would hold a Durable Object
in memory (billed by wall-clock time) around the clock. A support server gets a few messages a
day, so opspile polls instead: when nothing happened, a poll is two requests and a few hundred
milliseconds of the object's time. New messages show within a minute, edits, deletions and
reactions within about five.

Chrome over it with the CPU four times slower and prints the web vitals: load (LCP, time to a
usable list, long tasks), INP of the everyday interactions (opening threads, j/k, filters,
sorting, typing, @-mentions, profile cards), CLS, and what a live update costs
(`--runs=5`, `--origin=…`, `--profile[=step]`, `--trace=step`). Fake data only: it refuses any
origin but localhost.

To point the preview at production instead, sign in to the inbox in Chrome with remote
debugging on (port 9222), then run `npm run ui:session -- <inbox origin>`. It copies the Access
session cookie into `.dev-ui-session.json` (gitignored, never printed), and the preview switches
to the production API, read-only: writes are refused and the page's banner says so. Delete the
file, or run `npm run ui:session -- --clear`, to go back to fake data.

### Train the team order

Within a status, a team's inbox is ordered by the model in `ui/rank.js`: boosted trees (150
trees of depth 3, some 20 KB) over some fifty features of a thread, computed in the browser from the inbox entry (how long since the
last message, whether it waits on us, a customer's first message nobody at Adobe has answered,
Clef's urgency and resolved, a staff ✅, the kind, unseen by Adobe, reactions, what the last
message asks, …), in log-odds of "the team should turn to this one first". It is a
Bradley–Terry model whose strength is that score, learned from games of three kinds:

- **Judges.** A sample of threads (`pull`), paired in an Elo tournament where Clef says which
  comes first (`duel`); Haiku and Sonnet judge some of the pairs (`llm`), and you judge some
  (`judge`). Each pair is decided by the highest of those who judged it: you, then Sonnet, then
  Haiku, then Clef.
- **Picks.** When someone opens a thread by clicking it in the list, the inbox sends the threads
  on screen then, their places and their features to `POST /api/rank/pick` (table
  `rank_events`; not while viewing as someone else or searching; only in your own views, of a
  thread that exists). The cron deletes picks older than 90 days (`RANK_EVENTS_DAYS` in
  `src/rankevents.js`): by then the weekly training has fetched them into `.rank/events.jsonl`. The clicked thread wins over
  each of them: fully over those above it, less over those below it, which may not have been
  looked at.
- **Replies.** When the same person answers several customers on the same day, the customer
  answered sooner wins over the one answered later, each thread as it was when its customer
  wrote.

Each source is a share of the training (`DEFAULT_SHARES` in `scripts/rank-combo.mjs`: picks
30%, replies 20%, Sonnet 20%, you 15%, Clef 10%, Haiku 5%; a source without games gives its share
to the others), so Clef's thousands of games do not drown out the rest, and what the teams do
weighs more than what anyone says. The steps, each
reading what the ones before wrote into `.rank/` (gitignored; it holds production threads, so
it stays on your machine):

1. `npm run rank -- pull [--n all] [--alerts 0.1]` takes the threads of your teams' inboxes and
   your personal view (for the admin team, every team's, read as one of its members), with their
   messages, from the production API, read-only, with the session `npm run ui:session` copied.
   Alerts are a tenth of the sample. The sample before, and what was judged on it, moves to
   `.rank/<when it was pulled>/`, and is still trained on.
2. `npm run rank -- duel [--rounds 12]` plays the tournament with Swiss pairings: Clef reads
   two threads (their messages and what the inbox shows of them) and the team's policy
   (`POLICY` in `scripts/rank-lib.mjs`), and says which comes first, asked both ways round. More
   rounds add to the games played; changing what Clef is shown (`PROMPT_VERSION`) asks again.
   It calls Workers AI with `CLOUDFLARE_ACCOUNT_ID` (the Worker's account) and
   `CLOUDFLARE_API_TOKEN`, or the token of `wrangler login`.
3. `npm run rank -- llm [--judges haiku,sonnet] [--pairs 200]` has Claude models (on Bedrock,
   with a Bedrock API key in `AWS_BEARER_TOKEN_BEDROCK`, in `AWS_REGION`) judge the same games
   as Clef, shown the same, asked both ways round, with a sentence of why: the pairs you judged,
   then `--pairs` more. `--judges name=<model id>` adds others.
4. `npm run rank -- judge [--port 8796]` shows two threads of Clef's games side by side in the
   browser, and you pick the one the team should turn to first (← →, ↓ for "same", `s` to skip,
   `u` to undo). Then it shows what Clef, the Claude judges (with their reasons), the model and
   the old score said, and how often each agrees with you so far (Clef's also by how sure it
   was, and where asking it the other way round changed its mind). It can show any pair, pairs
   where one or both threads are still pending, the ones Clef was unsure of, or where the model
   and Clef, or the model and the old score, disagree; "Blind" hides the answers. Your answers
   go to `.rank/human.jsonl`. It follows a new sample by itself.
5. `npm run rank -- events` fetches the picks recorded since the last time
   (`GET /api/rank/events`, admin team) into `.rank/events.jsonl`.
6. `npm run rank -- train [--model boost|linear] [--trees 150] [--depth 3] [--shares click=0.3,…|counts]
   [--weights …] [--without a,b] [--dry-run]` fits the model on all samples, picks and replies, prints how often the model
   picks the winner of each source's games about a thread it was not trained on (five folds by
   thread: no game with a held-out thread is trained on, whatever its source), next to the hand-made score it replaces (`classicScore` in `ui/inbox.js`), and how
   often each judge agrees with you, and writes the model into `ui/rank.js` (between
   `// MODEL:` and `// END MODEL`). A feature seen in fewer than `--min-support` threads is not
   learned, and the policy's signs (`SIGNS` in `scripts/rank-combo.mjs`: resolved lowers a
   thread; waiting on us, unseen by Adobe and a first message nobody answered raise it) are
   kept: the trees are monotone in them (a split on such a feature must order its leaves so, as
   XGBoost's monotone constraints do); in a linear model (`--model linear`, L2 `--l2 30`) a
   weight the games would turn the other way is held at 0, and the training says which.
   `--without` leaves features out, to see what they are worth.
   Only feature names, thresholds and numbers are committed. A tree is `[feature, threshold,
   left, right]` or a leaf: the browser walks them (some 4 µs a thread), and D1 could as nested
   `CASE` expressions.
7. `npm run rank -- compare [--trees 150] [--depth 3]` puts the linear model next to boosted
   trees and a random forest (`scripts/rank-trees.mjs`, learned from the same games with the same
   pairwise loss), on the same folds: held-out accuracy per source, log loss, size and the time
   to score a thread.
8. `npm run rank -- weekly [--pr]` does it all once a week: a fresh session from the signed-in
   browser, the picks, a new sample, the tournament, the Claude judges on part of it, then the
   training; with `--pr`, the new weights go to a pull request against main (from a worktree of
   it, and only when main computes the same features). A bb automation runs it on Mondays.
9. `npm run rank -- behavior` looks at what the teams do instead: for every thread of the
   sample, whether someone on its team opened it in the inbox and how many read it, and for
   every time a customer wrote, whether and how soon Adobe answered; by kind, urgency, who has
   the next move, size, age, platform, team, and what the message says (a question, alarm words,
   thanks, its length, the time and day), with the odds of an answer within a day from a
   logistic regression, and how well the model, Clef's ratings and the old score pick the threads
   that were opened. It writes `.rank/behavior.md`.

A feature is added in `features()` of `ui/rank.js`, which the browser, the picks and the
training all run; train again after changing one. Picks keep the features they were sent with,
so a new feature is learned from picks only once the inbox computes it. `Rank.explain(entry)`
in the console lists what makes up a thread's score. Without a model (`const MODEL = null`) the
inbox orders by `classicScore`.

### Agents in the browser (WebMCP)

The inbox registers [WebMCP](https://developer.chrome.com/docs/ai/webmcp) tools, so an agent
in the browser (Gemini in Chrome, an extension) can work the inbox through the same UI as the
person signed in, instead of clicking through the DOM. Every tool changes what is on screen
(filters, the open thread, the reply box) and every write goes through the same endpoints as
a click, as that person. A read-only "view as" refuses writes.

| Tool | What |
| --- | --- |
| `get_inbox_state` | Viewer, team, filters, open thread, and counts per filter value |
| `filter_threads` | Set filters (and values to exclude), sort and team |
| `list_threads` | The threads shown, most relevant first |
| `search_threads` | Search on screen, as the search box does; the results, best match first, with the message that matched |
| `open_thread` | Open a thread (marks it read) and return its latest messages |
| `draft_reply` | Put a reply in the reply box for the person to send (in this browser only) |
| `post_draft` | Save a reply as the thread's shared draft, for the team (`base`: the draft it replaces; `sources`: what it rests on, which only the team sees) |
| `post_as_user` | Post a reply as the person, after a confirmation dialog |
| `post_as_bot` | Post a reply as the opspile app, after a confirmation dialog, where the channel lets the app post |
| `react_to_message` | Add or take off a reaction |
| `resolve_thread` | ✅ on the first message, or take it off again |

Tool output that carries message text or titles is marked `untrustedContentHint`, and
`post_as_user` and `post_as_bot` are marked `consequentialHint`. To try them, turn on
`chrome://flags/#enable-webmcp-testing` and open the inbox (`npm run ui:dev` works) with the
[Model Context Tool Inspector](https://chromewebstore.google.com/detail/model-context-tool-inspec/gbpdfapgefenggkahomfgkhfehlcenpd)
extension.

### Develop and deploy

**CI** ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs lint, tests and a build
check on every pull request. A push to `main` applies the D1 migrations and deploys
`helix-opspile-prod`. It authenticates with the repository secrets `CLOUDFLARE_API_TOKEN`
(an account token scoped to Workers scripts, R2, Queues, D1, Artifacts and Workers
Observability; it expires after a year) and `CLOUDFLARE_ACCOUNT_ID`, and reads the plain-text vars from the
secrets of the same name. Migrations must be additive, because they run before the new code
is live.

To deploy by hand instead: deploys go through the new Cloudflare CLI,
[`cf`](https://developers.cloudflare.com/cf/), which reads `cloudflare.config.ts` (`--mode
prod` or `--mode stage` selects the Worker). `cf deploy` and `cf dev` also build the inbox's
markdown bundle and the knowledge-base editor's (`src/ui-markdown.bundle.js` and
`src/ui-editor.bundle.js`, not committed; `npm run build` by hand).

```sh
npm install
npm run lint
cf auth create <profile> && cf auth activate <profile>  # once, for the target account
printf 'MS_CLIENT_ID=…\nMS_TENANT_ID=…\nPUBLIC_ORIGIN=https://…\nSTAFF_DOMAINS=…\n' > .env
npm run deploy:prod                                    # or deploy:stage
```

`cf` has no `keep_vars`: the plain-text vars are part of every deploy, so the config reads them
from the environment or `.env` and refuses to deploy without them. Secrets are declared by
name only; `cf deploy` checks that they exist on the Worker and keeps their values. `cf`
cannot set a single secret yet, so use
`npx wrangler secret put SLACK_BOT_TOKEN --name helix-opspile-prod`, or pass
`--secrets-file` to `cf deploy` (required for the first deploy of a new Worker). For
`cf dev`, put the bindings in an uncommitted `.dev.vars`.
